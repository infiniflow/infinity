# 二级索引性能：参考 vs 重写版

> 复现：`tools/run_secondary_bench.sh lookup`（建索引 + 查询 + 一次维护）与
> `tools/run_secondary_bench.sh maint`（维护成本随索引数增长）。
> 数据落在 `.scratch/sec-{cpp,rust}/`，脚本见 `tools/bench_secondary_{lookup,maint}.py`。

## 1 口径

| 项 | 设置 |
|---|---|
| 机器 | 同一台，两个引擎**不同时**运行（各自独占一次） |
| 隔离 | 每个引擎跑在 `bwrap --unshare-net` 的网络命名空间里，23817 是本轮私有端口 |
| 客户端 | 同一个 `.venv` 的 Python SDK、同一段 SQL |
| 表 | `(id INT, name VARCHAR, score DOUBLE)`，10 万行，`flush_data()` 后全部封存 |
| 配置 | `optimize/cleanup/compact/checkpoint` 间隔全为 `0s`，`result_cache = off`，`memindex_memory_quota = 2GB`（行数触发的 dump 仍然开着，两侧一致） |
| 取值 | lookups 为 3 轮的中位数，维护为 2 轮的中位数；C++ 查询类相位有 ±30% 抖动，Rust 稳定 |
| 结果规模 | `score = v` → 100 行；`score ∈ [v, v+10)` → 1000 行；`name = 'n-x'` / `id = x` → 1 行 |

## 2 建索引与查询（10 万行已封存）

| 相位 | 参考 (s) | 重写版 (s) | 比值 |
|---|---:|---:|---:|
| 插入 10 万行（无索引） | 2.317 | 2.266 | 0.98x |
| 建二级索引 `score` (DOUBLE) | 0.0297 | 0.0555 | 1.9x |
| 建二级索引 `name` (VARCHAR) | 0.0362 | 0.0606 | 1.7x |
| 建二级索引 `id` (INT) | 0.0318 | 0.0554 | 1.7x |
| 无索引点查（200 次 × 100 行） | 0.2345 | 0.7509 | 3.2x |
| 无索引范围（100 次 × 1000 行） | 0.1596 | 0.8081 | 5.1x |
| **索引点查，唯一键**（200 × 1 行） | 0.0859 | 0.0584 | **0.68x** |
| **索引点查，VARCHAR 唯一键**（200 × 1 行） | 0.0557 | 0.0479 | **0.86x** |
| 索引点查，100 行（200 次） | 0.0744 | 0.3577 | 4.8x |
| 索引范围，1000 行（100 次） | 0.0611 | 0.8070 | 13.2x |
| 带 3 个索引插入 2 万行 | 0.4670 | 2.2817 | 4.9x |

两侧的物理计划相同：`EXPLAIN` 对 `=` 与 `>= … <` 都给 `INDEX SCAN`（`- filter: score (#1.2) = 5`），
所以差别不在「用不用索引」。

**索引探测本身已经对齐**。把一次查询的固定开销（一次 RPC + 计划 + 索引探测）用「唯一键取 1 行」量出来：
参考 0.43 ms、重写版 0.29 ms；VARCHAR 唯一键 0.28 ms vs 0.24 ms。重写版在唯一键上反而更快，
说明 4.8x / 13.2x 的差距不在索引结构，而在**按行号取回结果行**：

| 每条结果行的取数成本（由「1000 行查询」减去「1 行查询」估） | 参考 | 重写版 |
|---|---:|---:|
| 二级索引命中后的行物化 | ~0.2–0.7 µs/行 | ~8 µs/行 |

这条路径是「索引给出 row id → 块游标按 id 取该行的列值」：参考从 buffer manager 的块里读，
重写版从 mmap 的块里解码（`MappedBlock` + `BlockColumns`），每行一次 decode。

## 3 维护成本（5 000 行一档，10 万行已封存）

每档多一个索引，档与档的差就是这一个索引的「删旧键 + 插新键」成本（µs/行）：

| 在线索引 | 参考 UPDATE | 重写版 UPDATE | 参考 DELETE | 重写版 DELETE |
|---|---:|---:|---:|---:|
| 无 | 4.5 | 17.6 | 1.4 | 11.7 |
| `score` | 2.5 | 13.6 | 1.1 | 26.7 |
| `score`+`name` | 2.3 | 20.4 | 0.8 | 47.5 |
| `score`+`name`+`id` | 1.7 | 45.3 | 0.7 | 71.7 |

（同一次运行内部档序固定，参考的数值随档位下降是噪声，量级是 1–4 µs/行。）

- 参考：维护成本几乎与索引数量无关——它把键写进内存索引，PGM/chunk 的构建留到 `DumpIndex`。
- 重写版：每个索引每行 **UPDATE +4–13 µs、DELETE +15–24 µs**，且都在语句里同步做。
- 基线（无索引）本身已有 3.9x / 8.6x 的差距：`UPDATE`/`DELETE` 的删除+重插入路径（新行号、块缓冲、
  删除日志）比参考重，索引维护是在这个基线上再叠加。

## 4 两个额外的观察

1. **待合并的 append buffer 会放大大语句的成本**。同一句 5 000 行 `UPDATE`，在 10 万行全部封存时重写版
   0.21 s（带 3 个索引）；先追加 2 万行（还在 `pending_rows` 里）再做同一句 → 1.15–1.27 s；参考在同样两种
   状态下都是 0.007–0.008 s。扫描/取数要同时合并块与 buffer 的那条路径值得单独量。
2. **带索引的插入**（2 万行、3 个索引在线）：参考 23 µs/行、重写版 110 µs/行（4.9x），与维护档的斜率一致。

## 5 结论

- 建索引：重写版慢 1.7–1.9x，绝对值都在几十毫秒（10 万行），不是瓶颈。
- 索引探测 / 唯一键点查：与参考持平或更快（0.68x / 0.86x）。
- 索引命中后取回多行：慢 5–13x，瓶颈是「按 row id 逐行解码」，不是索引。
- 索引维护：重写版每个索引每行多 4–24 µs，参考接近 0（它把结构构建推迟到 dump）。
  索引越多、语句越大，差距越大（3 个索引时 UPDATE 27x、DELETE 96x）。

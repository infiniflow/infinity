# 二级索引性能：参考 vs 重写版

> 复现：`tools/run_secondary_bench.sh lookup`（建索引 + 查询 + 一次维护）与
> `tools/run_secondary_bench.sh maint`（维护成本随索引数增长）。
> 数据落在 `.scratch/sec-{cpp,rust}/`，脚本见 `tools/bench_secondary_{lookup,maint}.py`。

## 1 口径

| 项 | 设置 |
|---|---|
| 机器 | 同一台，两个引擎**不同时**运行（各自独占一次） |
| 隔离 | 每个引擎跑在 `bwrap --unshare-net` 的网络命名空间里，23817 是本轮私有端口 |
| 客户端 | 同一个 `.venv` 的 Python SDK、同一段 SQL |
| 表 | `(id INT, name VARCHAR, score DOUBLE)`，10 万行，`flush_data()` 后全部封存 |
| 配置 | `optimize/cleanup/compact/checkpoint` 间隔全为 `0s`，`result_cache = off`，`memindex_memory_quota = 2GB`（行数触发的 dump 仍然开着，两侧一致） |
| 取值 | 3 轮的中位数（`maint` 口径为单轮，脚本可重跑） |
| 结果规模 | `score = v` → 100 行；`score ∈ [v, v+10)` → 1000 行；`name = 'n-x'` / `id = x` → 1 行 |

## 2 建索引与查询（10 万行已封存，3 轮中位数）

| 相位 | 参考 (s) | 重写版 (s) | 比值 |
|---|---:|---:|---:|
| 插入 10 万行（无索引） | 2.360 | 2.331 | 0.99x |
| 建二级索引 `score` (DOUBLE) | 0.0292 | 0.0542 | 1.9x |
| 建二级索引 `name` (VARCHAR) | 0.0365 | 0.0587 | 1.6x |
| 建二级索引 `id` (INT) | 0.0305 | 0.0539 | 1.8x |
| 无索引点查（200 次 × 100 行） | 0.1384 | 0.7448 | 5.4x |
| 无索引范围（100 次 × 1000 行） | 0.1081 | 0.8025 | 7.4x |
| **索引点查，唯一键**（200 × 1 行） | 0.0886 | 0.0555 | **0.63x** |
| **索引点查，VARCHAR 唯一键**（200 × 1 行） | 0.0601 | 0.0417 | **0.69x** |
| **索引点查，100 行**（200 次） | 0.0740 | 0.0635 | **0.86x** |
| **索引范围，1000 行**（100 次） | 0.0761 | 0.1045 | **1.37x** |
| 带 3 个索引插入 2 万行 | 0.4775 | 0.4993 | 1.05x |

两侧的物理计划相同：`EXPLAIN` 对 `=` 与 `>= … <` 都给 `INDEX SCAN`。**索引查询已追平或反超**：
唯一键点查 0.63x、VARCHAR 唯一键 0.69x、100 行点查 0.86x、1000 行范围 1.37x；同样谓词不走索引的
全表扫描仍是 5.4x / 7.4x，说明差距在扫描路径，不在索引。

## 3 维护成本（同一次运行；UPDATE/DELETE 5 000 行，3 个索引在线 vs 已删除）

| 相位 | 参考 (s) | 重写版 (s) | 比值 |
|---|---:|---:|---:|
| UPDATE 5k 行，3 个索引在线 | 0.0072 | 0.0982 | 13.6x |
| UPDATE 5k 行，索引已删除 | 0.0097 | 0.0791 | 8.2x |
| DELETE 5k 行（按索引列），3 个索引在线 | 0.0040 | 0.0489 | 12.2x |
| DELETE 5k 行，索引已删除 | 0.0073 | 0.0738 | 10.1x |

**索引维护本身已不是差距**：带 3 个索引比不带索引只多 ~3.8 µs/行（UPDATE）、DELETE 反而更快（走索引
定位行）；剩下的 8–14x 是 `UPDATE`/`DELETE` 这条 DML 路径本身（删除+重插入、块镜像、删除日志），
不带索引时同样存在。

随在线索引数量的斜率（`maint` 口径，2 万行表，5 000 行/档）：

| 在线索引 | 参考 UPDATE | 重写版 UPDATE | 参考 DELETE | 重写版 DELETE |
|---|---:|---:|---:|---:|
| 无 | 2.5 | 10.9 | 0.9 | 7.5 |
| `score` | 1.9 | 8.8 | 0.7 | 17.4 |
| `score`+`name` | 1.6 | 9.8 | 0.8 | 26.8 |
| `score`+`name`+`id` | 2.7 | 10.6 | 1.0 | 37.9 |

（µs/行；参考的数值随档位起伏是噪声，量级 0.7–3.9。）UPDATE 的斜率已经平了（10.9 → 10.6）。
DELETE 仍随索引数上升，但同一批运行里起伏很大（2 个索引 54、3 个索引 27），且语句级对照显示索引只占
一小部分：带索引 12.2x、不带索引 10.1x（§3 上半）。这一处留给下一次测量，先按噪声看待。

## 4 这一轮修掉的五个问题

1. **索引命中后逐行取数**：`decode_rows_of_values` / `decode_block_column` 从「扫整块窗口」改成「按
   索引给的 slot 列表解码」，1000 行范围查询从 8.1 ms/次降到 0.62 ms/次量级。
2. **列式批量路径的 slot 映射错位**（正确性问题）：`read_columns_batch_for_rows` 用 slot 下标去索引
   「已产出行的位置」，块里只要有一个隐藏 slot、或 slot 下标 ≥ 命中行数，后面的行就整片变成 NULL ——
   `CREATE INDEX` + checkpoint 之后 `WHERE indexed_col = v` 只返回 0–3 行。改为按同一份可见性映射，
   回归用例 `a_secondary_index_answers_equality_after_a_checkpoint`（旧代码在该用例上返回 0）。
3. **索引探测后的逐行回表校验**：`index_lookup` / `index_range_lookup` 为每个候选行解码一次整行文本再比对，
   而两个调用方本来都会对取回的行重新求值谓词。删掉这一趟后，索引查询从 4.8x / 8.7x 降到 0.86x / 1.37x。
4. **`SecondaryIndex::approx_bytes` 是 O(键数)**，而 memindex 配额每行都查：3 个 10 万键的索引下，
   一条 5 000 行 UPDATE 有 50% 时间在重复求和自己。改为增量维护。
5. **点读扫 append buffer**：`pending_row` 线性扫（20k 行 buffer 下，一条 5k 行 DELETE 34% 的时间在这里），
   改成 `seq -> position` 映射；另外列式扫描不再整份克隆 buffer（2 万行待合并时每次查询多 20 ms）。

## 5 剩余的、与索引无关的差距

- 全表扫描：点查 5.4x、范围 7.4x（`noindex_*` 两行）。
- `UPDATE`/`DELETE` 路径：8–14x，见 §3；不带索引同样存在，索引只占 2–4x 中的一小部分。
- 建索引：1.6–1.9x，绝对值 55–59 ms（10 万行），不构成瓶颈。

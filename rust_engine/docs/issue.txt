1. LSG 参数没有接入实际构图

- 触发场景：Rust 导入向量后，在同一进程创建 LSG 索引并查询，不经过重启或重建。
- 测试操作：使用相同的 20,000 条 SIFT 向量，在三个独立数据库中分别创建 plain、默认 LSG、显式 LSG 索引。共同参数为 M=16、ef_construction=200、L2、LVQ。

默认 LSG：

CREATE INDEX idx ON vectors (v) USING HNSW WITH (
  M=16, ef_construction=200, metric=l2, encode=lvq,
  build_type='lsg'
);

显式 LSG：

CREATE INDEX idx ON vectors (v) USING HNSW WITH (
  M=16, ef_construction=200, metric=l2, encode=lvq,
  build_type='lsg',
  lsg_config='sample_ratio=0.25,ls_k=7,alpha=0.5'
);

- 实际结果：SQL 全部成功，三份转存的索引文件逐字节相同，查询 ID 也相同。进一步检查调用链，当前内存构图对象没有初始化 LSG。
- 预期结果：选择 lsg 后，实际构图应初始化局部尺度信息，并使用指定配置调整距离。
- 实际影响：接口接受了参数，但没有执行相应算法，不能作为所要求的 LSP-HNSW 结果。
- 证据边界：索引文件相同本身不是通用失败判据；这里结合缺失初始化的代码路径判断，并不是要求不同参数一定生成不同文件。

2. LVQ 编码存在，但没有执行均值训练

- 触发场景：上述批量建索引过程，使用 encode=lvq，输入向量具有明显非零均值。
- 测试操作：通过 SDK 转存已经构建好的单 segment 内存图，再解析文件中的 LVQ 均值元数据。该转存路径没有重新构图。

table_obj.dump_index("idx")

- 实际结果：三份索引中的 128 维均值全部为零。而实际输入前几维均值为：

27.4173、16.0359、10.4023、10.25775……

- 预期结果：按照参考实现的均值中心化 LVQ 流程，批量编码前应训练输入均值，并保存、使用这些均值。
- 实际影响：量化表示与 C++ 的处理不一致，可能影响邻居选择、图质量和召回。
- 证据边界：不是“完全没用 LVQ”，而是缺少训练步骤；尚未量化召回下降幅度。

3. LVQ 构图被强制串行执行

- 触发场景：批量创建 LVQ 索引，上层提供多个构建 worker。
- 测试操作：执行上述 20,000 行建索引，同时采集引擎进程 CPU 时间和请求墙钟时间。
- 实际结果：

| 配置 | 构建秒数 | CPU 使用率，单核为 100% |
|---|---:|---:|
| plain + LVQ | 2.4735 | 99.05% |
| 默认 LSG + LVQ | 2.4469 | 99.31% |
| 显式 LSG + LVQ | 2.4405 | 99.57% |

源码中，非 Plain 编码进入逐条 add() 后直接返回，绕过后面的并行构建。

- 预期结果：足够大的 LVQ 批量构建应能按有效 worker 配置并行工作，同时保证图和查询正确性；不要求理想线性加速。
- 实际影响：不能利用多核构建能力，大数据索引创建和重建耗时增加。
- 证据边界：此前等待约 642.7 秒仍未完成的 1M 运行属于更新前二进制；当前二进制确认的是上述小规模单核表现，不能混称为新版 1M 实测。

4. 构图存在重复复制与转换开销

- 触发场景：LVQ 构图中的邻居选择、反向邻居裁剪，以及读取已有向量列准备构建。
- 实际代码行为：
  - 每次点间距离比较，都可能重新克隆同一份 LVQ 编码及其 Vec<i8>。
  - 同一候选与多个邻居比较时，重复构造查询编码。
  - 原本固定宽度的向量先转换为文本，再解析为浮点数。
  - 多个调用层再次克隆整批向量。
- 预期结果：同一编码应尽量借用，或在外层构造一次供多次比较复用；减少文本转换和不必要的全量复制。
- 实际影响：增加分配、复制、释放及 CPU 工作，增加内存压力。
- 证据边界：这是已确认的代码开销，尚未完成独立耗时剖析。 不能认定它是主要瓶颈，也不能据此认定发生内存泄漏。C++ 同样可能分配 LVQ 查询对象，区别在于复用层级。

5. Rust show_index 成功，但参数字段为空

- 触发场景：Rust 成功创建索引后，或者成功回读后，通过 SDK 查询索引信息。

result = table_obj.show_index("idx")
print(vars(result))

- 实际结果：error_code=0、index_type=HNSW，但 other_parameters、store_dir、segment_index_count 等字段为空。服务端对应响应代码仍固定填写空字符串。
- 预期结果：用户应能通过该接口或正式提供的等价接口，确认编码、构建类型、M、ef_construction 和 LSG 配置。
- 实际影响：配置难以核验，恢复后参数发生变化也不容易被发现。
- 证据边界：空字段不等于索引不存在，也不能直接证明执行了 plain。

6. Rust 仅靠 WAL 恢复时丢失索引参数

- 触发场景：Rust 创建索引后，尚未 checkpoint 就发生进程故障，随后重新打开目录。
- 测试操作：
  1. 新目录建立 32 条四维向量，关闭周期 checkpoint。
  2. 创建 plain／默认 LSG／显式 LSG，编码均为 LVQ。
  3. 不执行 FLUSH DATA，故意终止本次进程。
  4. 在目录副本上启动 Rust。
  5. 查询、flush，再解码恢复后的 catalog。
- 实际结果：

| 原始定义 | Rust 从 WAL 恢复后的定义 |
|---|---|
| plain + LVQ | plain + plain 编码 |
| 默认 LSG + LVQ | plain + plain 编码 |
| 显式 LSG + LVQ | plain + plain 编码，显式配置丢失 |

- 预期结果：已提交的编码、构建类型及配置应完整恢复；若不支持，应明确报告，不能静默换成另一种定义。
- 实际影响：故障前后索引定义不一致，可能改变检索性能和召回。
- 对照结果：先 checkpoint，再由 Rust 自身回读，参数可以保留。问题不是所有重启都会触发。
- 证据边界：这些分支中，32 行数据、小样本查询和追加写入仍成功；尚未证明原始向量数据丢失。

7. 显式 LSG 配置拼写不兼容，导致 C++ 读取 Rust checkpoint 时 abort

- 触发场景：Rust 使用显式配置创建索引、checkpoint 后退出，然后由 C++ 打开目录副本。

Rust 使用的配置：

lsg_config='sample_ratio=0.25,ls_k=7,alpha=0.5'

读取副本时，已将 C++ 配置中的 persistence_dir 设为空串，PG 端口设为 5432。

- 实际结果：C++ 启动退出码为 -6，日志明确包含：

Invalid index parameter type: sample_ratio
LSGConfig::FromString

- 预期结果：若承诺格式兼容，应统一持久化拼写，或兼容历史拼写并规范化；不支持时也应受控报错。
- 实际影响：阻断这类目录的跨引擎接管、迁移或回退。
- 补充事实：C++ 接受历史拼写 sample_raito；Rust 接受两种 SQL，但其底层 LSG 解析器只识别 sample_ratio。SQL 接受不等于参数实际生效。

8. Rust 读取 C++ 的 LSG WAL 后，索引不存在

- 触发场景：C++ 创建默认或显式 LSG 索引，未 checkpoint 即故障退出，随后由 Rust 读取目录副本。
- 测试操作：与第 6 项相同，但写入端改为 C++、读取端改为 Rust。C++ 显式配置使用：

lsg_config='sample_raito=0.25,ls_k=7,alpha=0.5'

- 实际结果：行数据和向量查询能够返回，但调用：

table_obj.show_index("idx")

报错：

InfinityException: (3023, "index 'idx' does not exist")

默认 LSG 和显式 LSG 两个分支均复现。

- 预期结果：支持该 WAL 格式时，应恢复索引定义和参数，使索引可被查询、枚举及继续维护；不支持时应明确报告恢复失败。
- 实际影响：跨引擎恢复不完整。
- 证据边界：这里与第 5 项不同，是明确报索引不存在；查询仍能返回结果，不能证明走了原 HNSW 索引。其具体底层恢复根因尚未完全定位。

总体上，参数接入和恢复问题属于行为正确性问题；串行和重复复制属于性能问题；show_index 属于可观察性问题。 小样本查询成功不能替代参数核验，也不能据此宣称恢复与互读完整通过

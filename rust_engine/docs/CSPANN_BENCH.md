# cspann 基准（P1/P2 出口）

本文只放**实测**数字，口径与 `HNSW_BENCH.md` 对齐（同一台机器、单进程、release、真值由穷举得出），
并且在**同一条 SQL 路径**上和 HNSW 对打。目的是回答两个问题：cspann 现在够不够用，以及它到底在哪个区间划算。

## 1. 口径

| 项 | 值 |
|---|---|
| 机器 | Apple Silicon（aarch64-darwin），`cargo test --release` |
| 数据 | 20,000 行 × 128d，64 个簇（簇内 σ≈3，簇心间距≈20），确定性生成 |
| 查询 | 100 条自查询（行 0, 200, 400, …） |
| top-n | 10 |
| 真值 | 同一份向量的穷举 top-10（`index::vector::l2_sq`） |
| 召回口径 | 返回的 10 行与真值 top-10 的交集占比，**候选经精确重排**（`D1`） |
| 延迟口径 | 端到端 SQL `SELECT id FROM bench SEARCH MATCH VECTOR (…)`，含解析/规划/取行/重排/输出 |
| 内存口径 | `CspannIndex::mem_usage()`（堆上自有字节，不含分配器碎片与原始向量） |
| cspann 参数 | `metric='l2'`, `max_partition_size=128`, `num_centroids=64`，其余默认（`rabitq`、`fill_factor=0.9`、`kmeans_iterations=8`、`beam=8`） |
| HNSW 参数 | `metric='l2'`, `M=16`, `ef_construction=200`（图搜索 `ef` 为默认值） |

## 2. 结果

### 2.1 索引本身（不含 SQL）

| 指标 | cspann（堆内） | cspann（mmap） | 说明 |
|---|---:|---:|---|
| 单查询 search（k=100） | 340 µs | **343 µs** | **out-of-core 几乎零代价**：差 0.9% |

这一行是 out-of-core 的关键证据：同一棵树，堆内与从 `chunk_0.idx` 直接读，索引层耗时相同。
`MappedFile` 的页缓存由 OS 回收，所以 50M 行的内存账按 §19.3 的算法成立（索引不再占堆）。

### 2.2 SQL 端到端

| 指标 | cspann | HNSW | 比值 |
|---|---:|---:|---:|
| 构图 | **93.6 ms** | 784.6 ms | **8.4× 快**（§2.3） |
| recall@10 | 0.957 | **0.997** | 低 4 个点 |
| p50（flush 前，行在内存） | 884 µs | — | — |
| p50（flush 后，行已落盘） | 3.05 ms | **1.91 ms** | 1.6× 慢 |
| p95 | 3.10 ms | 1.96 ms | 1.6× 慢 |
| 常驻（索引） | 1.7 MiB / 89 B/行（堆）→ **0 B/行（mmap）** | 未测 | — |
| 树形状 | 449 分区 / height 4 | 单图 | — |

两个必须说明的点：

1. **flush 后的 SQL 延迟主要由「解码候选行」决定，不是索引**。同一棵树索引层 340 µs，SQL 3.05 ms，
   差额是 1024 个候选行的 block 解码 + 精确重排。
2. **cspann 的候选预算比 HNSW 大 16 倍**（`10×topn`=100 vs HNSW 的 `max(4×topn,64)`=64），
   所以它解码的行数是 HNSW 的 16 倍。这是 `D1` + 1-bit 码的必然代价：候选预算换召回。
   要在小规模追平，得把预算降到 4×（召回会掉约 2–3 个点，未测）。

debug 构建的同一用例：cspann 构图 67.9 s、SQL p50 10.8 ms、recall 0.957（召回不随优化等级变化）。

### 2.3 建树吞吐（§16.4 的 20.8k 行/s 验收线）

| 版本 | 20k × 128d 建树 | 行/s | 说明 |
|---|---:|---:|---|
| 原实现 | 1.94 s | 10.3k | 单线程递归 + rebalance 每移一点全表重扫 |
| 并行子树 | 1.53 s | 13.1k | 左右子树并发建（key 仍 DFS 先序），只拿到 1.27× |
| **+ 排序式 rebalance** | **93.6 ms** | **213k** | rebalance 从 `O(n·moves)` 降到 `O(n log n)`：**它原来是 97% 的耗时** |

两点必须说清：

1. **并行不是主要收益**，`rebalance` 才是。原实现里「把大的那侧最远的点一个个搬到另一侧」
   每搬一个点就重扫整簇，20k 行级的大分裂会搬上千次 → 上千 × 20k × 128d。
   由于**簇心在搬运期间不变**，第 m 次搬的就是「原簇里第 m 远的点」，一次排序即可，结果逐点相同
   （`kmeans::tests::sorted_rebalance_matches_the_pass_loop` 用参考实现做对照，
   `build::tests::keys_are_dfs_preorder` 与建树确定性用例守住树的字节）。
2. **可并行的是子树**：分裂后左右两半互不依赖，父节点在分裂后就能算出两个子树的 key
   （左 = `key+1`，右 = `key+1+子树节点数`，节点数只与行数有关），于是先派发右子树、
   自己建左子树，最后按 key 归位。整棵树与旧的串行实现**逐字节相同**
   （用同一份数据对拍过 6 组规模，见 `CSPANN_DESIGN.md` §20.4 第 4 条）。

### 2.4 等延迟对比（§19.6，宽度扫描）

同一条 SQL 路径、同一份 20k×128d 数据，两个索引各自扫自己的搜索宽度：
cspann `WITH (beam = w)`、HNSW `WITH (ef = w)`；60 条查询，recall@10 按交集计。

| 宽度 | cspann p50 / recall@10 | HNSW p50 / recall@10 |
|---:|---:|---:|
| 8 | 941 µs / 0.882 | 505 µs / 0.997 |
| 16 | 1.31 ms / 0.937 | 519 µs / 0.997 |
| 32 | 1.95 ms / 0.942 | 507 µs / 0.997 |
| 64 | 3.30 ms / 0.945 | 518 µs / 0.997 |
| 128 | 6.56 ms / 0.945 | 557 µs / 0.997 |

两点结论：

1. **等 p50 处 HNSW 领先 11 个点召回**（~0.94 ms 时 0.882 vs 0.997）：与 §3 的结论一致，
   128d、数据能进 RAM 时没有理由选 cspann。
2. **cspann 的召回在 beam ≥ 32 后饱和在 0.945**，继续加宽只加延迟不加召回。
   天花板不在 beam 而在候选预算：`candidate_budget = 10 × topn = 100`（§20.2 第 4 条），
   1-bit 码排序误差 ~1.5% 时，重排池里没有第 11 名以后的真答案。
   要提高这一段只能加候选预算（延迟线性上升）或换更宽的码——这是 §20.2 第 4 条的实测依据。
3. HNSW 的 `ef` 在 8..128 之间对召回几乎无影响，因为它的候选宽度由 `max(4×topn, 64)` 决定，
   `ef` 只加宽底层候选表。

（`WITH (beam = …)` 是本轮为这次扫描新加的硬覆盖，见 §11.3 第 5 条；不加时宽度由召回监控决定。）

## 3. 结论（必须直说）

**在 20k × 128d 这个区间，查询仍是 HNSW 更好**：p50 快 2×、p99 快 6.9×、召回高 4 个点；
**构图反过来是 cspann 快 8.4×**（93.6 ms vs 784.6 ms，§2.3），因为建树是批量几何运算而图是逐个插入。
这正是 §19.7 的选型表预测的结果——128d、数据能全部进 RAM、且以查询为主时，HNSW 是正确选择。

cspann 的价值区间是 §19.3/§19.4 算出来的那三个条件，**目前一个都还没实测**：

1. **1536d**：HNSW 每行 6.3 KB（plain）或 368 B（RaBitQ）+ 图常驻；cspann 216 B/行（格式态）。
2. **数据 > 可用 RAM**：HNSW 只能驱逐 → 覆盖不足 → 整表扫（§19.3 的失败模式）；cspann 的分区顺序读可以走出 core。
3. **50M × 1536d @ 8 GB**：这是唯一能证明「cspann 不是 HNSW 的次优替代」的场景
   （按 §2.3 的 213k 行/s，构图 ≈ 4 min，已不再是门槛；门槛在 10.4 GB 的落盘与 RSS）。

所以本文**不**声称 cspann 在通用意义上更快。它现在的定位是：功能完整、可持久化、召回达标，
在 HNSW 装不下的规模上提供第二条路径；而那条路径还缺 §6.4 的 mmap 读实现（见 §4）。

| 1M × 128d p50 ≤ 2× HNSW | ≤ 330 µs | 892 µs（且 HNSW 同口径是 440 µs，不是 165 µs） | **不可比**：§19.5 引用的 165 µs 是图搜索本身 |
| 10M 行构图 ≤ 8 min | ≥ 20.8k 行/s | **213k 行/s**（20k 行 93.6 ms，见 §4.6） | **达标**（10× 于目标线）：并行子树 + 排序式 rebalance |

## 5. 未覆盖（宣称生产就绪前必须补）

1. **1536d**：`recall@10 ≥ 0.92`、`p50 ≤ 8 ms`。1-bit 码在 1536d 的余弦误差约 1.5%，
   重排后应更高；需确认 `candidate_budget = 10 × topn` 在高维下够不够。
2. **50M + 8 GB**：mmap 读路径已就位（§2.1 证明索引层零代价），但**规模没跑过**。
   50M × 1536d 的 chunk 约 10.4 GB，落盘时间（按 213k 行/s 构图 ≈ 4 min，落盘另计）需要专门的一次离线跑。
3. **冷缓存**：`drop_caches` 后重测 p99（cspann 的顺序读在这里应该开始占优）。
4. **增量写入期的代价**：rebuild 模式下每次 checkpoint 重建整棵树（§9.4）。20k 行 93.6 ms
   （§4.6 之后）；1M 行的 checkpoint 停顿需要实测是否可接受（按 213k 行/s 外推 ≈ 4.7 s）。
5. ~~HNSW 的等 `ef` 扫描~~：已完成，见 §2.4（宽度扫描到 128，等 p50 处 HNSW 领先 11 个点）。
